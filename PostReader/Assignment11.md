## Результат всего задания

Небольшое приложение получает публикации из сети, показывает список, позволяет открыть полный текст и найти публикации по заголовку. Пользователь видит загрузку, успешный результат, отсутствие публикаций или ошибку с возможностью повторить запрос.

Источник — учебный JSONPlaceholder, без регистрации и API-ключа. Документация/ответ проверены при выдаче:

- [Описание API](https://jsonplaceholder.typicode.com/).
- Список: `https://jsonplaceholder.typicode.com/posts`.
- [Один объект для изучения формата](https://jsonplaceholder.typicode.com/posts/1).

У публикации есть `userId`, `id`, `title`, `body`. Это искусственные учебные данные, не реальные новости. Серверные ID сохраняются при декодировании/повторной загрузке, новый UUID для тех же публикаций не создаётся. Для деталей достаточно уже загруженной публикации; запрос автора или комментариев не нужен.

## Теория по этапам

### Сейчас, перед этапом 1

- Повтори Decodable/Codable, JSONDecoder и Data.
- Объект JSON и массив объектов: чем отличается форма данных и тип результата.
- Обязательное свойство и Optional: отсутствие значения и неверный тип — не одно и то же.
- Identifiable: идентичность серверного объекта, а не случайный ID каждой загрузки.
- Повтори throws/try/do-catch и отличие успешного декодирования от проверки результата.

Это закрепление, не чтение всей документации заново. JSON с четырьмя полями достаточно, без обёртки старого менеджера.

### Перед этапом 2

- Основы HTTP: URL, GET, ответ сервера и status code. HTTP-ошибка, транспортная ошибка и ошибка декодирования — разные причины неудачи.
- URLSession и HTTPURLResponse.
- async/await, async throws, место вызова асинхронной функции. await как возможная приостановка, а не команда «запустить на другом потоке».
- Минимум о Task и отмене; без изучения всего concurrency сразу.

Источники:

- [Swift Book: Concurrency](https://docs.swift.org/latest/documentation/the-swift-programming-language/concurrency/) — сначала только Defining and Calling Asynchronous Functions, затем нужные части о Tasks/отмене.
- [Apple: URLSession.data(for:delegate:)](https://developer.apple.com/documentation/foundation/urlsession/data(for:delegate:)).

### Перед этапом 3

- SwiftUI .task и время жизни асинхронной работы экрана.
- MainActor: изоляция состояния интерфейса; не нужно самостоятельно разбрасывать DispatchQueue по проекту.
- ProgressView, состояние загрузки и повторная попытка.
- Повтори State, единого владельца данных, List/NavigationStack, локальный поиск.

Актуальная [документация SwiftUI .task](https://developer.apple.com/documentation/swiftui/view/task(name:priority:file:line:_:)). Названия дополнительных параметров/перегрузок зависят от SDK; не требуется использовать новые аргументы имени или приоритета. Сначала изучи основное действие и связь с жизненным циклом View.

## Этап 1 — модель без сети и интерфейса

1. Посмотри формат одного объекта API и создай собственную модель публикации.
2. Подготовь небольшой локальный JSON-массив из двух своих публикаций: разные ID, заголовки и тексты. Не получай эталон кодированием той же модели, которую затем проверяешь: исходные данные задай независимо.
3. Преобразуй JSON в модели без настоящего запроса и без View. Проверочный запуск может быть отдельным консольным экспериментом; он не должен сам выполняться при каждом запуске iOS-приложения.
4. Проверь не только количество: все четыре поля, ID и порядок должны совпасть с заранее заданным ожиданием.
5. Сам предложи ещё два входа: корректный пустой результат и некорректные данные. До запуска напиши, что ожидаешь и какую ошибку заметит каждый сценарий. Не используй try? или пустой массив, чтобы скрыть неизвестную ошибку всего разбора.

На ревью — модель, место проверочного запуска и твои три сценария «вход → ожидание → факт». Имена и реализацию не выдаём заранее. Автоматический тестовый фреймворк пока не обязателен.

Первое действие: в конце Questions/Understanding.txt добавь короткий план — что описывает модель, откуда берётся ID и где проверишь декодирование без интерфейса. 3–5 предложений достаточно, старые ответы не удалять. После обсуждения — самостоятельная реализация, без бесконечного дописывания плана.

Сейчас сеть и экраны не реализовывать. Для этого этапа не нужно заранее изучать весь async/await.

## Этап 2 — настоящий запрос без SwiftUI

После принятия этапа 1 изучи темы сети и реализуй получение списка из `/posts` через URLSession с async/await.

Требования:

- Получение данных отделено от построения интерфейса; компонент передаёт результат либо ошибку, не печатает вместо возвращаемых данных и не создаёт тестовые публикации сам.
- Проверяется HTTP-ответ: успешными считаются статусы 200–299. Не пытайся выдать любой ответ сервера за нормальный список.
- Корректный JSON `[]` — успешный пустой результат. Сбой сети, неуспешный HTTP-статус и повреждённый JSON не превращаются в такой результат.
- Причина ошибки не теряется. Конкретные типы ошибок выбираешь сам.
- Только GET: не добавлять/редактировать/удалять публикации на сервере.

Проверки по собственным входам и ожиданиям: успешный запрос, отсутствие подключения, неуспешный HTTP-ответ, некорректное тело и корректный пустой ответ. Реальный `/posts` не обязан возвращать все нужные для тестов случаи; нужен контролируемый способ подать тестовый ответ. Его можно отдельно обсудить после первой реализации — заранее не требуем протоколов, собственного URLProtocol или сложной архитектуры.

Один живой запрос не заменяет проверки ошибок; временная недоступность учебного API не считается ошибкой твоей модели. Не меняй системные настройки/права ради тестирования.

## Этап 3 — интерфейс и состояние загрузки

- При первом открытии начинается загрузка, во время неё виден индикатор; синхронное сетевое чтение не блокирует интерфейс.
- Успех показывает заголовки публикаций. Нажатие открывает правильный полный текст, ID публикации и ID автора.
- Корректный пустой ответ отличается от ошибки.
- При ошибке видны понятное сообщение и повторная попытка; затем можно получить нормальный список.
- После успеха доступна явная перезагрузка кнопкой. Для этого задания при новой попытке прежний список заменяется загрузкой, затем новым результатом или ошибкой — сохранять старый контент при сбое не требуется.
- Повторные нажатия не создают параллельную пачку запросов. Нужен один владелец загруженного списка; детали не держат независимо синхронизируемую копию всей ленты.
- Обычное возвращение из деталей не запускает запрос заново. Пользовательская перезагрузка — отдельное действие, новый запуск приложения — новая загрузка.
- Завершённая отменой работа экрана не должна показывать пользователю «нет интернета» как обычную ошибку; базовую отмену изучаем при подключении .task.
- Поиск по заголовку локальный, без учёта регистра, крайние пробелы игнорируются. Пустой запрос показывает весь загруженный список; нет совпадений — отдельное сообщение. Ввод текста не вызывает сеть, строка поиска сохраняется при явной перезагрузке.

Конкретный enum состояния, struct/class и распределение файлов — твой выбор. Не задаём заранее готовую ViewModel и не требуем MVVM. До реализации коротко обозначь владельца данных и условия переходов экрана; это один план, а не отдельный экзамен.

## Этап 4 — итоговая проверка

Сначала свои ожидания, потом запуск:

- Успех, корректный пустой ответ и ошибка с последующим успешным повтором.
- Загрузка не блокирует экран, повторная кнопка не плодит запросы.
- Переход/возврат из деталей сохраняет правильную публикацию и не делает лишний запрос.
- Поиск, отсутствие совпадений и перезагрузка с сохранённым запросом.
- Серверные ID и поля не заменяются новым UUID и не перепутаны после отбора.
- Отмена асинхронной работы не выдаётся за сетевую ошибку.

Тесты должны включать управляемые данные/ошибки, не только зависеть от доступности публичного API. Агент может автоматизировать согласованные сценарии по поручению. На приёмке различаем код, тестовые ожидания и реально выполненные действия; новые косметические требования не добавляем бесконечно.
